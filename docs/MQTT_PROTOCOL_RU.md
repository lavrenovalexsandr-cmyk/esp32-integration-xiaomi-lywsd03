# MQTT-протокол Xiaomi LYWSD03MMC

- Версия протокола: **1**
- Статус: согласованный MQTT-контракт v1; управление HA-сущностями выполняется интеграцией
- Область действия: обмен между ESP32-шлюзом и Home Assistant для BLE-датчиков Xiaomi LYWSD03MMC

## 1. Общие правила

Каждый шлюз имеет стабильный `DEVICE_ID`, предоставляемый Platform Core. Все Xiaomi-топики шлюза находятся в его собственном namespace:

```
esp32/<DEVICE_ID>/xiaomi/
```

`DEVICE_ID` — идентификатор шлюза, а не MAC датчика. Команды всегда отправляются конкретному шлюзу; широковещательные команды не используются.

- MQTT QoS: **1** для всех перечисленных сообщений.
- Команды и результаты команд: **retain=false**.
- Снимки обнаруженных устройств и реестра: **retain=true**.
- Последние измерения: **retain=true**.
- JSON-кодировка: UTF-8.
- Во всех JSON-сообщениях протокола присутствует `version: 1`.
- MAC в payload и topic нормализуется к верхнему регистру и формату `AA:BB:CC:DD:EE:FF`.
- Неизвестные поля получатель должен игнорировать. Неизвестная версия протокола не должна обрабатываться как версия 1.

### 1.1. Топики

| Направление | Топик | Retain | Назначение |
|---|---|---:|---|
| ESP → HA | `esp32/<DEVICE_ID>/xiaomi/discovered` | Да | Текущий список обнаруженных, но не сохранённых датчиков |
| ESP → HA | `esp32/<DEVICE_ID>/xiaomi/registry` | Да | Список датчиков, сохранённых в NVS шлюза |
| ESP → HA | `esp32/<DEVICE_ID>/xiaomi/sensor/<MAC>/state` | Да | Последние измерения датчика |
| HA → ESP | `esp32/<DEVICE_ID>/xiaomi/command/add` | Нет | Добавление датчика и bind-key |
| HA → ESP | `esp32/<DEVICE_ID>/xiaomi/command/remove` | Нет | Удаление датчика |
| ESP → HA | `esp32/<DEVICE_ID>/xiaomi/command/result` | Нет | Результат команды |

Для каждого шлюза используются собственные топики. Подписка на namespace одного шлюза не должна принимать команды другого шлюза.

## 2. Обнаруженные датчики

Шлюз публикует retained-снимок датчиков, которые были обнаружены по BLE, но отсутствуют в его сохранённом реестре.

Пример:

```json
{
  "version": 1,
  "sensors": [
    {
      "mac": "A4:C1:38:12:34:56",
      "rssi": -68
    }
  ]
}
```

Правила:

1. Датчик считается обнаруженным в течение **5 минут** после последнего принятого advertising-пакета.
2. При каждом новом advertising-пакете обновляется RSSI и срок актуальности.
3. Сохранённые на этом шлюзе датчики не входят в `discovered`.
4. Если датчик удалён из реестра, но продолжает обнаруживаться, он снова появляется в `discovered`. Это необходимо для UI: после удаления датчик снова имеет статус **New**, а сохранённый — **Save**.
5. Когда список меняется, шлюз публикует полный актуальный снимок, а не отдельные дельты.
6. Если список опустел или все записи истекли, шлюз публикует retained-сообщение с пустым массивом `sensors`. Пустой retained payload для этого топика не используется.

Список относится только к конкретному шлюзу. Один и тот же MAC может одновременно присутствовать в списках обнаружения нескольких шлюзов.

## 3. Сохранённый реестр

Реестр отражает датчики, для которых bind-key сохранён в NVS данного шлюза.

Пример:

```json
{
  "version": 1,
  "sensors": [
    {
      "mac": "A4:C1:38:12:34:56"
    }
  ]
}
```

Правила:

- Источник истины — NVS и реестр Xiaomi-драйвера на ESP32. Home Assistant не редактирует реестр напрямую.
- Шлюз публикует полный retained-снимок при запуске MQTT, после успешного добавления и после удаления.
- Пустой реестр публикуется как `{"version":1,"sensors":[]}`.
- Интеграция Home Assistant хранит актуальный снимок отдельно для каждого шлюза и не смешивает реестры.
- После удаления датчик исключается из `registry`; если он ещё обнаруживается, он присутствует в `discovered`.

## 4. Измерения

Для каждого сохранённого датчика используется отдельный state topic:

```
esp32/<DEVICE_ID>/xiaomi/sensor/<MAC>/state
```

Пример:

```json
{
  "version": 1,
  "temperature": 23.4,
  "humidity": 48.2,
  "battery": 87
}
```

Поля:

| Поле | Тип | Единица / значение |
|---|---|---|
| `temperature` | number | °C |
| `humidity` | number | % |
| `battery` | integer | % |

Публикуются только фактически полученные и успешно расшифрованные измерения. Если поле ещё неизвестно, оно может быть опущено. Значения не должны заменяться нулями или фиктивными значениями.

Шлюз публикует обновление после получения новых валидных измерений. Сообщение retained, чтобы Home Assistant получил последнее значение после переподключения.

Home Assistant integration подписывается на этот топик и создаёт отдельные сущности температуры, влажности и батареи на основании registry. Единицы, device_class и state_class задаются самой интеграцией; firmware не публикует Xiaomi MQTT Discovery.

Доступность сенсорных сущностей наследуется от availability соответствующего шлюза. Отдельный availability topic на каждый датчик в версии 1 не вводится. Это означает, что доступность шлюза не гарантирует, что сам датчик недавно передавал данные.

При подтверждённом удалении датчика шлюз удаляет retained state topic публикацией пустого retained payload. В Home Assistant XSM сначала выполняет локальное удаление: сохраняет persistent tombstone, сразу удаляет сущности и дочернее устройство и игнорирует устаревшие retained snapshots для этого MAC. Если шлюз доступен, команда удаления отправляется в фоне; её подтверждение не требуется для локального удаления. Tombstone снимается после получения registry от шлюза, в котором MAC уже отсутствует.

## 5. Команда добавления

Топик:

```
esp32/<DEVICE_ID>/xiaomi/command/add
```

Пример:

```json
{
  "version": 1,
  "request_id": "a81f92c4",
  "mac": "A4:C1:38:12:34:56",
  "bind_key": "0123456789ABCDEF0123456789ABCDEF"
}
```

Требования:

- `request_id` — идентификатор запроса, непустая строка длиной не более 64 символов. Интеграция генерирует уникальное значение для каждой операции.
- `mac` — MAC датчика в каноническом формате.
- `bind_key` — ровно 32 шестнадцатеричных символа, представляющих 16 байт.
- Команда отправляется только в namespace выбранного шлюза.
- Команда не retained.
- Firmware проверяет формат полей и передаёт ключ драйверу для сохранения в NVS.
- Bind-key запрещено логировать, отражать в ответе или публиковать в любом другом топике.

Успешное добавление приводит к обновлению `registry`. Если датчик продолжает обнаруживаться, он исключается из `discovered`.

## 6. Команда удаления

Топик:

```
esp32/<DEVICE_ID>/xiaomi/command/remove
```

Пример:

```json
{
  "version": 1,
  "request_id": "b72f31a0",
  "mac": "A4:C1:38:12:34:56"
}
```

Удаление адресуется конкретному шлюзу. При успешном удалении:

1. запись датчика удаляется из NVS/реестра;
2. публикуется обновлённый `registry`;
3. удаляется retained state датчика;
4. если датчик всё ещё обнаруживается, он остаётся или снова появляется в `discovered`.

Повторное удаление отсутствующего датчика возвращает `not_found`.

## 7. Результат команды

Обе команды возвращают результат в:

```
esp32/<DEVICE_ID>/xiaomi/command/result
```

Пример успешного результата:

```json
{
  "version": 1,
  "request_id": "a81f92c4",
  "action": "add",
  "mac": "A4:C1:38:12:34:56",
  "result": "success"
}
```

Допустимые значения `action`: `add`, `remove`.

Допустимые значения `result`:

| Результат | Значение |
|---|---|
| `success` | Операция выполнена |
| `already_exists` | Датчик уже сохранён на этом шлюзе |
| `not_found` | Датчик не найден в реестре (для удаления) |
| `full` | Реестр заполнен |
| `invalid_argument` | Некорректные аргументы или формат команды |
| `storage_error` | Ошибка чтения/записи хранилища |
| `busy` | Операция временно невозможна из-за занятого ресурса |
| `not_initialized` | Xiaomi-компонент не инициализирован |

Результат содержит исходные `request_id`, `action` и нормализованный `mac`. Он никогда не содержит bind-key.

QoS 1 допускает повторную доставку сообщений. Поэтому операции должны быть безопасны при повторе: повторное добавление возвращает `already_exists`, повторное удаление — `not_found`. Интеграция сопоставляет результат с ожидающей операцией по паре gateway + request_id.

## 8. Правило одного шлюза на один датчик

Один MAC может быть сохранён только в реестре одного шлюза одновременно.

- BLE-обнаружение одного MAC несколькими шлюзами разрешено.
- Перед отправкой add интеграция проверяет retained-реестры всех известных шлюзов.
- Если MAC уже сохранён на другом шлюзе, интеграция отклоняет добавление и не отправляет команду.
- Интеграция также резервирует MAC на время ожидающей операции add, чтобы не отправить параллельные команды на два шлюза.
- После успешного remove MAC снова может быть добавлен на другой шлюз.
- Firmware не имеет глобального знания о других шлюзах и самостоятельно не обеспечивает межшлюзовую блокировку. Это правило координируется интеграцией Home Assistant; прямые команды в обход неё находятся вне этой гарантии.

Retained registry offline-шлюза также учитывается: потеря связи сама по себе не освобождает MAC.

## 9. Home Assistant устройства и сущности

- Xiaomi measurement entities не создаются через MQTT Discovery и не регистрируются в Platform Core.
- Home Assistant integration создаёт отдельное дочернее устройство и три сущности (temperature, humidity, battery) для каждого MAC из retained `registry`.
- Идентификаторы дочернего устройства и сущностей строятся из `DEVICE_ID` шлюза и MAC датчика, чтобы одинаковые MAC на разных шлюзах не приводили к коллизиям.
- В `device_info` дочернего устройства задаётся `via_device=("esp32", DEVICE_ID)`, связывающий его с общим устройством шлюза.
- Интеграция подписывается на `esp32/+/xiaomi/sensor/+/state` и принимает измерения только после получения identity шлюза от ESP32 Manager. До получения registry измерения кэшируются, если identity уже известна; сообщения, пришедшие раньше identity, отбрасываются.
- Доступность сущностей следует за `esp32/<DEVICE_ID>/availability`. Это доступность шлюза, а не гарантия недавнего BLE-обмена с датчиком.
- При локальном запросе удаления XSM сразу удаляет три сущности и дочернее устройство, сохраняя tombstone до подтверждения очистки шлюзом. При исчезновении MAC из registry интеграция также удаляет дочернее устройство; при появлении MAC снова создаёт его.
- Комнаты/Areas не передаются по MQTT. Пользователь назначает Area средствами Home Assistant.

## 10. Ограничения реализации

Xiaomi-драйвер поддерживает реестр до 16 датчиков на шлюз. Firmware также содержит кэш последних измерений на 16 датчиков. После перехода на HA-managed entities лимит `PLATFORM_HA_MAX_ENTITIES` в Platform Core больше не ограничивает количество Xiaomi-сущностей: эти сущности не регистрируются в Platform Core. Однако лимит реестра драйвера и ёмкость firmware-кэша остаются самостоятельными ограничениями и должны проверяться отдельно. MQTT-протокол не обещает поддержку большего числа датчиков, чем позволяют драйвер и firmware.

## 11. Переподключение и запуск

После запуска MQTT и после каждого переподключения шлюз должен опубликовать актуальные retained-снимки `discovered` и `registry`. Последние измерения остаются доступны через retained state topics.

Интеграция использует retained-снимки как текущее состояние шлюза. Команды не должны накапливаться в брокере: retained для команд запрещён. После потери MQTT-соединения интеграция не должна считать неподтверждённую команду add успешной: она ожидает результат либо сообщает об ошибке/тайм-ауте и сверяет состояние со следующим снимком реестра. Удаление в XSM выполняется локально сразу, а очистка на шлюзе является фоновой best-effort операцией; tombstone сохраняется до подтверждения отсутствия MAC в registry.

Availability самого шлюза публикуется универсальным Platform Core в `esp32/<DEVICE_ID>/availability` с retained и Last Will. Xiaomi-специфичный availability topic не добавляется.

## 12. Безопасность

- Bind-key передаётся только в add-команде.
- Bind-key не хранится Home Assistant-интеграцией и панелью.
- Bind-key не попадает в retained-сообщения.
- Firmware не логирует ключ и очищает временные буферы после использования.
- Командные топики должны быть доступны на запись только доверенному Home Assistant/клиенту, а шлюзам — на чтение команд и публикацию собственных состояний.
- MQTT транспорт использует TLS согласно настройкам Platform Core.

## 13. Область версии 1

Версия 1 не определяет OTA/Restart/Factory Reset, управление комнатами, отдельный availability каждого датчика, передачу bind-key обратно в HA, широковещательные команды или межшлюзовую блокировку на стороне firmware.
